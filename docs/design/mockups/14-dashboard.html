Dashboard convergence

The dashboard was never part of the original design pass — DESIGN_SYSTEM.md §8 covers Topic/Learn, Path + Checkpoint and Quiz. It is 39 classes across 246 lines of styles.css, roughly a fifth of the file, and it is the Home tab. This page tests one question: does it fit the existing primitives, or does it need new ones?

Companion to styleguide.html · tokens as at sw.js v97 · nothing new declared
Finding

It fits. Every block maps onto a primitive that already exists, and the watermark it needs is already specified. What the dashboard actually has is a colour problem: five tinted surface treatments, four of them built on hues that are not in the token set. That is a convergence job, not a design job — with one real decision, which is what carries the hero once per-topic colour is gone.

The checkpoint watermark

A checkpoint spans a whole stage, so there is no single word for the watermark to carry. Rather than omit it — which left the card looking bare — one fixed character stands for “checkpoint” throughout — 站 (zaam6), decided. All four candidates below are absent from the taught vocabulary, so none can be confused with something a learner is meant to recognise. Shown at real size and opacity.

4 · Rule corrections this surfaces

§3.6 — the emoji exception names the wrong screen

It reads “kept where they are genuine wayfinding — the dashboard topic grid”. There is no topic grid on the dashboard. renderHomeScreen() renders Topics, not Home, and that is where .topic-grid lives. So the exception should read the Topics category grid, and the dashboard's own emoji — two tile badges, the review icon, the path icons, 🎉 in a title — fall outside it. Renaming renderHomeScreen() → renderTopicsScreen() belongs in phase 3.

§3.4 — two progress bars, and whether that breaks the rule

The dashboard shows a track per path. §3.4 forbids “two bars measuring different things a centimetre apart”, which was about stage progress versus whole-path progress on the same screen. Two paths measured identically in one list are a set, not competing indicators. Proposed clarification: one progress indicator per fact, and sibling facts share one form. That permits this list and still forbids the original defect.

§Watermark — applies to the hero, and it is currently inverted

The rule says the oversized character is “the word being studied, not decoration”. The hero ships a hardcoded 字 (zi6) — decoration by definition. The hero already knows the topic, so it can carry that topic's anchor word. Proposed amendment: the watermark carries the word being studied; where a band spans a whole stage rather than a single word, it carries the fixed checkpoint character instead. That is the one exception, and naming it in the spec is what stops the next hardcoded 字 (zi6) appearing somewhere else. Note this makes 字 (zi6) correct for exactly one stage — beginner-s1, First Words — which is probably how it got there.

§2 — a dashboard entry is missing entirely

Everything above is composition of existing primitives, so the spec needs one §2 entry recording the order and what each block is, not a new primitive contract: hero → path progress → review → jump-to, each preceded by a .section-label, one fill on the screen, and the tab bar at the bottom because Home is a top-level destination (§3.10).
