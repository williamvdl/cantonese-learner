16 · Stepper scale & checkpoint context

Two questions raised on device against v109. Section 1 settles the stepper's painted size; section 2 settles whether the stage strip belongs on the checkpoint hub.

1 · Stepper painted scale

v109 built the stepper at .node--sm = 20px, which is what styleguide.html specifies. On a real phone it reads spindly — the nodes are the smallest thing on a screen where they are also the primary lateral navigation. Note the timeline's own rail nodes are 32px, so the same marker is currently two very different sizes depending on which screen you are on.

All three below have a correct 44px touch target; only the painted circle changes. Compare each against the tier pills and title beneath it, which are unchanged.

S20 — as built

The styleguide value. Smallest thing on screen; the 1px connectors dominate it.

S24

Splits the difference. Still clearly subordinate to the 32px rail node, but the digits are legible and the row has weight.

S28

The base .node size, so --sm would go unused here. Closest to the timeline's 32px; risks competing with the tier pills.

Where I'd land: S24. It fixes the complaint without making the strip compete with the tier row directly beneath it, and it keeps --sm meaning "smaller than a rail node", which is the distinction the primitive exists to carry. S28 makes the stepper the loudest element in the chrome stack and leaves --sm with no call sites. Scoped as .stepper .node, so the primitive itself is untouched and any future --sm user is unaffected.

2 · Stage context on the checkpoint hub

The hub is the last member of its stage, but it currently has no stage context and no lateral navigation — only a back arrow. You cannot go from a half-finished checkpoint to the topic you want to revise without returning to the timeline. Adding the contextual row and stepper closes that, and makes the strip's end diamond mean "you are here" rather than only "there is an end".

The real question is the hairline. The row's track measures stage topic progress everywhere else. On the hub, the page also reports checkpoint activity progress ("1 of 2 reviewed"). Two indicators of different quantities on one screen is the §3.4 defect by name, so the two must be told apart by form, not just position.

H1 — reject

Hairline switched to measure checkpoint activities. Same element means stage progress on one screen and activity progress on the next — 50% here is a different fact from 50% one tap earlier.

H2

Hairline keeps measuring stage topics (full, because every topic is done). Activity progress moves to .segs — a countable set, one pip per activity. Different fact, different form.

H3

H2, plus the hero trimmed: the stage name is dropped from the hero because the row and strip already carry it twice over. Leaves the diamond and the count.

Where I'd land: H3, but it should ship after the diamond progress ring, not before. Once .mk exists, the hub's hero diamond carries activity progress as a ring and the .segs strip in H2/H3 becomes redundant — so building .segs here first means building something the next deploy deletes. H3's hero trim and the context row are independent of that and could ship either side.

The one new state this needs

The strip's end diamond has to read as current while staying a diamond. .node--cp and .node--current collide today: --cp is declared later, so milestone wins and the diamond looks unvisited. The proposal is an explicit .node--cp.node--current — a milestone fill with a white glyph, matching how .node--cp.node--done was resolved in v108. It keeps §4 intact: the shape says checkpoint, the fill says you are here, and no fifth colour is introduced.
